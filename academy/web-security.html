Web Security

Govern web-facing risk across exposure, application controls, cloud edges, and remediation workflows. This course teaches how to identify web attack surface from your asset inventory, prioritize web-facing findings by business context, produce evidence-backed remediation decisions, and communicate web security posture to executives in business-risk language.

~2.5 hours 6 modules + knowledge checks Practitioner Certification eligible
Before you begin: This course uses the Surface, Findings, and Risks modules. The Cloud Security course is recommended prior to this one, as web security findings appear within the broader cloud posture picture.
1

Web Attack Surface

Mapping the public-facing exposure that creates your organization's web security risk boundary.

What constitutes the web attack surface

The web attack surface is everything publicly accessible from the internet that an attacker could interact with. In a cloud environment, this is broader than "our website" — it includes load balancers and API gateways, storage accounts with public access configured, public cloud endpoints, CDN origins that expose backend URLs, identity provider login pages, and any service endpoint not restricted to internal networks.

Each component of the web attack surface has its own risk profile: Public endpoints — APIs, login pages, and application interfaces that process user input are the highest-value targets for injection and authentication attacks. Public cloud storage — storage buckets or blob containers with public read access can expose sensitive data directly, with no exploitation required. Identity surfaces — public-facing authentication flows are targets for credential stuffing, brute force, and OAuth abuse. API gateways — incorrectly configured API authorization can expose backend business logic.

In the platform — Identify public exposure from assets and findings
1
Navigate to Surface > All Assets. Filter by the tag "public" or the configuration attribute "publicly accessible." Review the list — these are your internet-facing assets.
2
Navigate to Findings. Filter by the control category "Public Exposure" or "Storage Encryption." High-severity findings in these categories represent direct web attack surface risk.
3
For each public-facing asset, click into the asset detail. Review: is this asset intentionally public? Does it handle sensitive data? Is there a business justification for the public exposure? Document this context in the asset notes field.
4
Cross-reference your public assets against your business process map. Which business processes depend on these public endpoints? This is the business impact context for any web-facing finding.
Map your web attack surface: List all assets tagged or configured as publicly accessible. For each, document: intentional or accidental exposure, data handled, and linked business process.
Identify unintentional public exposure: Flag any public-facing asset that should not be publicly accessible. These require immediate remediation — unintentional public exposure is your highest-priority web security gap.
Confirm attack surface documentation: Ensure your web attack surface inventory is current — any change to public-facing infrastructure should update this list within 48 hours.
Knowledge Check
Which type of web attack surface exposure typically creates the most direct data exposure risk with the least exploitation barrier?
Publicly accessible login pages — they expose the authentication system to credential stuffing attacks.
Public cloud storage containing sensitive content — data is directly accessible without any exploitation, authentication bypass, or skill requirement from an attacker.
API gateways with overly permissive rate limiting — they enable high-volume enumeration attacks.
CDN origins with exposed backend URLs — they can be accessed directly to bypass CDN-level controls.
Move on when you've mapped your web attack surface and identified any unintentional public exposure.

Common Web Risks

The misconfiguration, authentication, and header risks that dominate web security findings.

The most common web security findings in cloud environments

CloudSignals surfaces web security findings from cloud resource configurations — not from active application scanning. This means the findings reflect configuration state, not runtime behavior. The most common web security finding categories in cloud environments are:

Finding categoryWhat it meansTypical severity
Public storage exposureStorage bucket or blob has public read or write access enabled — data is accessible to anyone with the URLCritical
Missing security headersLoad balancer or CDN isn't enforcing HSTS, CSP, X-Frame-Options, or similar headers — clients are exposed to injection and clickjackingMedium–High
Weak authentication configurationMFA not enforced on admin console, session timeout not configured, or token validity period is excessively longHigh
Unencrypted endpointsAPI or application endpoint accepts HTTP (unencrypted) connections — credentials and session tokens are exposed in transitHigh
Insecure API configurationAPI Gateway has authentication disabled, CORS is overly permissive, or rate limiting is absentHigh–Critical

Why configuration findings matter more than runtime findings for governance

Runtime application vulnerabilities (SQL injection, XSS, IDOR) require application-level scanning or manual testing to detect — they are outside the scope of CSPM. However, configuration-based web risks are persistently present: a missing security header isn't intermittently present, it's absent on every request until it's added. This makes configuration findings more governable — they can be continuously monitored, their presence/absence is deterministic, and fixing them produces verifiable results on the next scan.

Review findings by web security category: Filter findings by the categories in the table above. Identify your most prevalent category — this is your systematic web security gap.
Triage all public storage exposure findings: Any storage bucket with public access enabled and sensitive content must be triaged same-day regardless of your standard triage cadence.
Review security header coverage: Confirm your primary internet-facing endpoints have HSTS, CSP, and X-Frame-Options configured. If not, create treatment plans.
Knowledge Check
Why are configuration-based web findings more governable than runtime application vulnerabilities like SQL injection?
Configuration findings are lower severity — they don't require the same level of governance rigor as runtime vulnerabilities.
Configuration findings are persistently present, continuously monitorable, and their remediation produces deterministic, scanner-verifiable results — unlike runtime vulnerabilities that require manual testing to detect and verify.
Configuration findings are harder to exploit, so they don't need to be prioritized as urgently in the remediation queue.
Runtime vulnerabilities are managed by the application team, not the security team, so they are out of scope for CSPM governance.
Move on when you've triaged public storage exposure findings and reviewed security header coverage.

Web Evidence

What constitutes valid web security evidence and what falls short of governance requirements.

Evidence types for web security controls

Web security evidence falls into four categories: Configuration exports — screenshots or API outputs from cloud consoles confirming security header settings, storage access policies, and TLS configuration. Scan results — CSPM findings showing control pass/fail status for web-facing resources. Penetration test reports — third-party assessments of web application behavior (these cover runtime behavior that CSPM cannot). Attestations — named reviewer confirmations that a control is operating as expected, used for controls that cannot be automatically evaluated.

A common mistake is treating screenshots alone as sufficient web security evidence. Screenshots capture a point-in-time visual state but don't document the control mechanism, the scan methodology, or whether the state was intentional. A governance-grade evidence artifact for a "security headers enforced" control includes: a scan result or configuration export, a timestamp, a reviewer attestation confirming the headers are correctly configured and actively enforced, and linkage to the specific Assessment Objective it satisfies.

In the platform — Build web security evidence artifacts
1
Navigate to a web-security-relevant UCB control (e.g., "Enforce HTTPS on all public endpoints"). Open the Evidence Requirements panel and review what artifact types are expected.
2
Navigate to the Evidence Fabric. Upload the relevant evidence artifact — for a TLS enforcement control, this is a scan result showing TLS 1.2+ enforced on the target resource.
3
Link the artifact to the Assessment Objective. Set the evidence type (automated scan = higher base confidence than screenshot). Assign a reviewer.
4
After reviewer attestation, verify the AO status updates to "Satisfied." Confirm the linked UCB control's confidence score improves. These changes are visible to any auditor reviewing your evidence chain.
Audit web security evidence quality: For your top 5 web security UCB controls, confirm each has a scan result or configuration export (not just screenshots) linked as primary evidence.
Assign reviewers to web evidence artifacts: Confirm every web security evidence artifact has a named reviewer. Unreviewed artifacts contribute zero to AO satisfaction.
Identify web controls requiring pen test evidence: For controls that scanner data cannot verify (runtime behavior, authentication flows), confirm a penetration test is scheduled and its report will be linked as evidence.
Knowledge Check
Why are screenshots alone insufficient as web security evidence?
Screenshots are too large to store efficiently in the Evidence Fabric and degrade over time.
Screenshots capture a point-in-time visual state but don't document the control mechanism, scan methodology, or whether the state was intentional — they must be accompanied by configuration exports, logs, or scan results to be audit-valid.
Screenshots are not accepted by any major compliance framework as evidence — only API exports and scan results qualify.
Screenshots expire after 30 days and must be replaced, creating unsustainable evidence maintenance burden.
Move on when you've audited web security evidence quality and confirmed reviewer assignments.

Web Security in Cloud Posture & Asset Governance

How CloudSignals connects web-facing findings to asset ownership and governance accountability.

Web findings as a subset of cloud posture

In CloudSignals, web security findings are not separate from cloud posture findings — they are a subset of them. A finding on an API Gateway, load balancer, or storage bucket with public access is both a cloud posture finding and a web security finding. The distinction matters for routing: web security findings on customer-facing assets have higher business impact than equivalent findings on internal infrastructure, because the attack path from a web finding to customer harm is shorter.

The asset governance connection is critical. When a web-facing finding is created, it attaches to the asset where the misconfiguration was detected: the load balancer, the storage account, the API gateway. The asset's managed entity and owner determine who receives the finding for triage. If the asset is unowned, the finding becomes an orphaned signal — no one routes it, no one remediates it, and the exposure window stays open.

In the platform — Prioritize web-facing findings by business context
1
Navigate to Findings. Filter by asset tag "public" or control category "Public Exposure." These are your web-facing findings.
2
For each web-facing finding, click through to the linked asset. Review: managed entity, data sensitivity, and business process linkage. Findings on assets handling PII or linked to customer-facing business processes are highest priority.
3
Confirm every web-facing asset has an owner. Any public-facing asset without an owner is a critical governance gap — unowned public assets should be flagged for immediate ownership assignment.
4
Create a filtered view or saved report: "Web-facing Critical assets with open High/Critical findings." This is your recurring review list for web security governance meetings.
Confirm all web-facing assets are owned: Any public-facing asset without an owner and managed entity is a governance gap. Assign ownership before the next triage cycle.
Create a web security priority view: Build a saved filter: public assets + High/Critical findings + PII/Critical sensitivity. This is your web security watchlist.
Link web assets to business processes: Confirm your primary web-facing assets are linked to business processes in the Risks module. This is the context required for business-impact prioritization.
Knowledge Check
How does CloudSignals connect a web-facing finding (e.g., a public API Gateway misconfiguration) to governance accountability?
Web-facing findings are automatically escalated to the CISO without requiring asset linkage.
The finding attaches to the specific asset (the API Gateway) it was detected on — the asset's managed entity and owner determine who is responsible for triage and remediation.
Web security findings are handled by a separate web security team and don't follow the standard asset governance model.
CloudSignals groups all web findings under a single "Web Security" managed entity regardless of the asset's actual ownership.
Move on when all web-facing assets are owned and you've created a web security priority watchlist.

RiskOps Treatment for Web Findings

Creating evidence-backed remediation decisions for web-facing risk.

Treatment workflow for web security findings

Web security findings follow the same RiskOps treatment workflow as any other finding — but with specific evidence requirements that reflect the web attack surface context. When creating a treatment plan for a web-facing finding, the evidence requirement should specify: a post-remediation scan confirming the control now passes, plus a configuration export showing the specific change made (e.g., the bucket policy now blocks public access, or the load balancer rule now enforces HSTS).

For web findings where remediation requires a deployment or migration, the treatment type should be Mitigate with an interim compensating control — for example, restricting the vulnerable endpoint to specific IP ranges, adding a WAF rule to block exploitation attempts, or requiring additional authentication. The compensating control buys time while remediation is in progress and reduces risk during the remediation window.

In the platform — Create a remediation project with evidence requirements
1
From a web-facing Critical or High finding, click Create treatment plan. Link it to the asset and confirm the managed entity owner is pre-populated.
2
Select the treatment type: Remediate if the fix can be implemented immediately, or Mitigate if a compensating control is needed while the full fix is in progress.
3
Set the evidence requirement: Required evidence = scan result after fix + configuration export showing the specific change. Add this to the evidence requirement field so the verifier knows what to collect at closure.
4
Set the target date based on your SLA policy. For a publicly-accessible Critical finding, this should be within 24–72 hours for the compensating control and within 7 days for full remediation.
5
Submit the plan. Navigate to Projects and confirm it appears with the correct SLA tier. Monitor the plan's status until the verifying scan confirms closure.
Create treatment plans for all web-facing Critical findings: No Critical finding on a public-facing asset should remain without a treatment plan and owner assignment.
Implement compensating controls for deferred remediations: For web findings where remediation will take more than 72 hours, confirm a compensating control (WAF rule, IP restriction, enhanced monitoring) is in place.
Verify evidence requirements are set before submission: For every web security treatment plan, confirm the evidence requirement field specifies what proof will be collected at closure — before you submit the plan.
Knowledge Check
A public-facing API endpoint has an insecure CORS configuration that cannot be fixed until a migration completes in 3 weeks. A WAF rule is in place restricting cross-origin requests. What is the appropriate treatment?
Accept the risk with a permanent exception — the WAF rule makes the residual risk acceptable indefinitely.
Mitigate — the WAF rule is a compensating control reducing residual risk while remediation is in progress. Document the control, set the remediation target to the migration date, and track to verified closure.
Remediate — applying the WAF rule counts as remediating the underlying misconfiguration.
Defer — the finding should not be triaged until the migration completes and the correct CORS configuration can be verified.
Move on when all Critical web findings have treatment plans and compensating controls are in place for deferred remediations.

Executive Communication

Translating web security posture into business-risk language that executive audiences can act on.

What executives need from web security reporting

Executive audiences don't need technical details — they need business context. A web security report that says "47 misconfigured HTTP security headers identified across 12 load balancers" doesn't help an executive make a decision. A report that says "Our customer-facing payment portal is serving responses without the browser security controls that prevent credential theft and clickjacking. Three customer-facing services are affected. Remediation is underway and should be complete by Friday — the exposure window is approximately 5 business days" gives a decision-maker everything they need.

The Ask Vision feature in CloudSignals can help draft web security narratives from finding data — but every narrative must be reviewed for accuracy before sharing with leadership. Vision doesn't know your business context, customer contracts, or regulatory obligations. The security analyst is responsible for adding that context and ensuring the narrative is accurate before distribution.

In the platform — Draft and validate an Ask Vision web risk narrative
1
Navigate to Vision > Ask Vision. Enter a web security question: "What are the highest-risk web-facing exposures in our environment and what business processes are affected?"
2
Review the Vision response. Check: are the cited findings accurate and current? Are the business process impacts correctly attributed? Are there any overstatements or understatements?
3
Edit the narrative to add: the remediation status for each identified issue, the expected resolution timeline, and any regulatory or contractual implications specific to your organization.
4
Add your reviewer attestation. The narrative is now governance-grade — it can be used as a briefing document for the CISO, board, or relevant business stakeholders.
5
Export the narrative. Store a copy in the Evidence Fabric linked to the relevant UCB controls and business processes — it serves as evidence that web security posture is being actively communicated and governed.
Draft a web security executive brief: Using Vision and your own review, produce a one-page brief explaining current web-facing risk in business terms — suitable for your CISO or board.
Validate and attest the narrative: Before distributing any AI-assisted narrative, confirm every cited finding is current and accurately described. Add your attestation.
Schedule monthly web security reporting: Add a recurring calendar entry to generate and distribute a web security posture brief to your security leadership team.
Knowledge Check
What makes a web security narrative appropriate for executive audiences?
It includes a complete list of all open web security findings sorted by CVSS score, so executives can see the full picture.
It translates technical findings into business risk language — stating what is exposed, the likelihood given current state, the business impact (customer, regulatory, reputational), and remediation status — without requiring technical expertise to interpret.
It is generated entirely by Vision AI without human editing, ensuring objectivity and eliminating analyst bias.
It is endorsed by an external penetration testing firm confirming the findings are genuine and exploitable.
Move on when you've drafted, validated, and attested a web security executive brief.
