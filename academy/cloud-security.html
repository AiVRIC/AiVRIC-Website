Cloud Security

Use CloudSignals to operate continuous multi-cloud posture management across AWS, Azure, GCP, and OCI. This course covers the CSPM model, scan lifecycle, misconfiguration detection, the boundary between framework compliance scores and UCB governance, cloud evidence for audit readiness, and Vision-assisted investigation and remediation planning.

Multi-Cloud CSPM Model

How CloudSignals evaluates posture continuously across cloud providers.

What CSPM is and what it fundamentally does

Cloud Security Posture Management (CSPM) is the continuous evaluation of cloud resource configurations against security policies. Where traditional security scans run periodically and produce point-in-time reports, CSPM runs continuously — evaluating every connected resource against every active policy check on a defined cadence, typically every 24 hours or on-demand.

CloudSignals supports CSPM across AWS, Azure, GCP, and OCI using a unified policy library. Each provider has provider-specific policy checks mapped to the UCB — so an IAM finding on AWS and a similar finding on Azure both map to the same UCB control, enabling cross-cloud governance without maintaining separate policy programs per provider.

Scan Lifecycle

What happens during a scan, what can be missed, and how to interpret scan results.

The scan lifecycle

A scan cycle in CloudSignals has four phases: Authentication — the connector authenticates to the provider using its configured credentials. Discovery — the connector enumerates all resources in-scope (accounts, regions, resource types) within the permissions granted. Evaluation — each discovered resource is compared against each active policy check. Recording — findings are created for failed checks, existing findings for passing checks are closed, and asset inventory is updated.

The critical constraint is permissions. A connector only sees what it has read access to. If an account is added but not included in the IAM policy, or if a region is excluded, those resources are silently not evaluated — they don't generate findings, but they're not compliant either. They're invisible. This is why connector scope verification is a critical governance activity, not just an initial setup step.

In the platform — Review scan results by provider and account
1
Navigate to Settings > Connectors. For each connector, review: last scan timestamp, status (Success/Failed/In Progress), and resource count discovered.
2
Click into a connector. Review the scan scope: which accounts, regions, and resource types are covered. Compare against your actual cloud footprint — are there any gaps?
3
Navigate to Surface > Cloud Resources. Group by provider. For each provider, confirm the resource count aligns with your expectations. Unexpectedly low counts may indicate scope gaps.
4
Navigate to Findings and filter by Provider. Review the finding distribution across providers — are all providers generating findings? A provider with zero findings is likely a scope gap, not a clean environment.
Verify all connectors completed successfully: Any connector with a failed or stale last-scan state represents a gap in your posture data. Investigate and resolve.
Cross-reference scope vs. footprint: For each provider, confirm the connector scope covers all active accounts, subscriptions, and projects.
Investigate zero-finding providers: A cloud provider with no findings is almost certainly a scope or permission issue — not a clean environment.
Knowledge Check
Why does a completed scan not automatically mean all resources were evaluated?
Some resource types are too large for a single scan cycle and are batched across multiple scans.
Scan scope is limited by the permissions granted to the connector — accounts, regions, or resource types lacking read access are silently excluded from evaluation.
Resources created within the last 24 hours before a scan are excluded until the next full scan cycle.
Completed status only confirms authentication succeeded — resource evaluation is a separate process tracked in the Findings module.
Move on when you've verified connector scope and confirmed all providers are generating findings.

Misconfiguration Detection

Understanding what the scanner evaluates and what the finding context tells you.

How policy checks become findings

A policy check is a rule that evaluates a specific resource configuration property. For example: "S3 bucket public access block is enabled" or "Azure storage account minimum TLS version is 1.2." When a check evaluates a resource and the property does not meet the expected state, a finding is created. The finding records: the resource that failed, the specific check, the expected state, the actual state, the severity, and the remediation guidance.

Understanding the anatomy of a finding is important because the remediation guidance tells you exactly what to change — but context tells you whether you should. An S3 bucket with public access enabled is a finding — but if that bucket is intentionally public (a static website), the finding is a known acceptable state. CloudSignals allows you to suppress or accept findings for intentionally misconfigured resources, so they don't inflate your posture score with known-good exceptions.

In the platform — Drill into a failed cloud check and investigate context
1
Navigate to Findings. Filter by Provider = AWS (or your primary cloud). Filter by Severity = Critical. Click into the first finding.
2
Review the finding detail: the resource ARN or ID, the specific policy check that failed, the expected configuration state, and what was actually found.
3
Click View linked asset. Review the asset's managed entity, owner, data sensitivity, and environment tag (prod/staging/dev). This context determines how urgently to act.
4
Review the Remediation guidance in the finding detail. This is provider-specific — for AWS misconfigurations it includes the exact CLI or console steps to fix the configuration.
5
If the finding is an intentional exception (e.g., a public bucket that should be public), click Suppress or Accept with justification, so it no longer inflates your active finding count.
Review all Critical cloud findings: Work through every Critical finding and confirm it is a genuine misconfiguration (not an intentional exception). Create treatment plans for confirmed gaps.
Suppress or accept intentional exceptions: For resources that are intentionally configured in a way that triggers a finding (e.g., public CDN buckets), document the justification and accept the finding to keep your posture signal accurate.
Map your top 5 finding types: Identify the five most common misconfiguration types in your environment. These are your systematic gaps — they likely have a shared root cause that one policy fix can address.
Knowledge Check
What is the relationship between a policy check and a finding in CloudSignals?
A policy check is a compliance framework requirement; a finding is a technical observation that may or may not map to that requirement.
A policy check is a rule evaluated against a resource's configuration; a finding is created when the check fails — inheriting the policy's severity and remediation guidance.
Policy checks and findings are separate systems — checks run in the compliance module, findings are generated by the vulnerability scanner.
A finding generates a policy check — the scan evaluates the finding against the policy after an engineer reports it.
Move on when you've reviewed Critical cloud findings and handled intentional exceptions.

Compliance Framework Posture vs. UCB Governance

Understanding why a high framework score doesn't mean you're compliant.

The fundamental distinction

CloudSignals shows compliance framework posture scores — percentages representing how many of your cloud resources pass the policy checks mapped to SOC 2, ISO 27001, PCI DSS, NIST CSF, and other frameworks. These scores are useful directional indicators. They are not the same as compliance.

The gap between a posture score and actual compliance is evidence. A framework posture score measures scanner metadata: whether your cloud resources are configured in ways that pass automated checks mapped to framework controls. Actual compliance requires evidence of control effectiveness: proof that the control not only exists but produces the expected risk reduction over time. An assessor issuing a SOC 2 Type II report needs both — and the Type II requirement specifically demands evidence of consistent operation over the audit period, not just a passing configuration at a point in time.

A 95% CIS AWS Benchmark score is not SOC 2 compliance. Framework posture scores are valuable posture signals and triage aids. They are inputs to your UCB governance program, not the program itself. Use the Framework Explorer to understand what controls need evidence — then collect that evidence through the Evidence Fabric.
In the platform — Map a finding to evidence and RiskOps work
1
Navigate to Governance & Assurance > Framework Explorer. Select your primary compliance framework. Review your current posture score and drill into the lowest-scoring control categories.
2
Click into a failing control category. Review which specific checks are failing, and which UCB controls they map to. The UCB control is where you need to collect evidence — not the framework control directly.
3
For the lowest-scoring UCB controls, navigate to the Evidence Fabric and check whether evidence exists. A low posture score with no linked evidence means no auditor can verify compliance — scanner data alone is insufficient.
4
For failing checks that represent genuine gaps (not intentional exceptions), navigate to the linked finding and create a treatment plan. The treatment plan in RiskOps closes the loop between the framework gap and the remediation commitment.
Review your framework posture score: Generate the Framework Explorer view for your primary compliance framework. Note the score and identify the lowest-scoring domains.
Confirm UCB evidence for framework controls: For your top 10 framework controls, verify evidence exists in the Evidence Fabric — a passing posture check without linked evidence is not audit-ready.
Create RiskOps treatment plans for genuine gaps: For each control category with a posture score below your target threshold, create treatment plans for the underlying findings.
Knowledge Check
What is the key difference between a compliance framework posture score and UCB-based governance?
Framework posture scores are real-time; UCB governance is updated only during quarterly reviews.
Framework posture scores reflect whether scanner metadata aligns with framework control mappings; UCB governance requires evidence of control effectiveness — the scanner result is an input, not the proof.
UCB governance covers all frameworks simultaneously; posture scores are framework-specific and cannot be compared across frameworks.
Framework posture scores are more accurate because they are based on automated checks, whereas UCB governance relies on potentially subjective human attestations.
Move on when you've reviewed framework posture, confirmed UCB evidence, and created treatment plans for genuine gaps.

Cloud Evidence & Audit Readiness

What makes cloud configuration data governance-grade rather than just scan output.

The requirements for audit-grade cloud evidence

A cloud configuration export from a CSPM scan is raw scan output. It becomes governance-grade evidence when it meets four requirements: Timestamped — the data is attributed to a specific scan run with a documented collection time. Linked to a specific Assessment Objective — the evidence is mapped to the control assertion it satisfies. Reviewed and attested — a named reviewer has confirmed the evidence accurately represents the control state. Scoped to the assessment period — the evidence was collected during the relevant audit period of performance, not before or after.

Cloud evidence that lacks any of these properties may be useful for internal monitoring but will not satisfy an external assessor's evidence requirements. The audit package generation process in CloudSignals automatically enforces these requirements — but only if evidence is properly collected and linked in the Evidence Fabric before package generation.

In the platform — Prepare a cloud posture summary and evidence package
1
Navigate to Reports > Cloud Posture Summary. Generate a summary for the current period — this is the executive view showing finding distribution, remediation velocity, and posture trend.
2
Navigate to the Evidence Fabric. Filter for cloud-sourced evidence artifacts (automated/scanner type). Review their freshness — are the most recent scan results linked to the corresponding UCB controls?
3
For controls that rely on cloud scan data as primary evidence, confirm each evidence artifact has: a scan timestamp, an Assessment Objective linkage, and a reviewer attestation.
4
Navigate to Reports > Audit Package. Generate a package filtered to cloud-security-relevant UCB controls. Preview it for completeness before considering it audit-ready.
Confirm scanner evidence is linked: For your top 20 UCB controls by framework criticality, verify each has a linked cloud scan result in the Evidence Fabric.
Generate and review a cloud posture summary: Export the posture summary and confirm it accurately reflects your environment. Identify any gaps before sharing with stakeholders.
Test audit package generation: Generate a test audit package for your primary framework. Review what "Not Assessed" controls remain — these are your evidence gaps before the next audit.
Knowledge Check
Which of the following makes a cloud configuration export "audit-ready" rather than just scan output?
It was generated by an enterprise-licensed CSPM tool and is in a standard JSON or CSV format auditors can parse.
It is timestamped, linked to a specific Assessment Objective, reviewed and attested by a named reviewer, and collected during the relevant audit period of performance.
It shows 100% pass rate for all policy checks in the relevant framework — any failing check disqualifies the export as audit evidence.
It has been uploaded to the cloud provider's compliance portal and acknowledged by the provider's trust team.
Move on when you've confirmed evidence linkage and tested audit package generation.

Vision-Assisted Cloud Investigation

Using AI to surface patterns, prioritize clusters, and plan remediation — with human review required.

What Vision brings to cloud security investigation

Cloud security investigations often involve hundreds of findings across multiple providers, accounts, and regions. Vision AI accelerates this by doing three things that are difficult to do manually at scale: Pattern recognition — identifying that 40 findings across different accounts all represent the same root cause (e.g., an IAM policy template deployed across all accounts that is overly permissive). Priority surfacing — ranking finding clusters by combined business impact, not just raw severity. Narrative generation — producing a readable summary of the highest-risk patterns for security managers and executives who need context without raw scan data.

In the platform — Use Vision to investigate a cloud risk pattern
1
Navigate to Vision. Click Ask Vision and enter a cloud security investigation question: "What are the highest-risk IAM misconfigurations across our AWS accounts?"
2
Review the response. Check the assumptions panel — which findings, accounts, and resources was the analysis based on? Are all the findings current?
3
If Vision identifies a finding cluster with a shared root cause, click through to the linked findings. Verify the cluster is accurate — AI groupings can sometimes include false positives if the pattern matching is too broad.
4
Use the Vision-generated cluster analysis as the basis for a treatment plan. Create a single remediation plan addressing the shared root cause, referencing the Vision analysis as supporting context.
5
Draft an Ask Vision cloud risk narrative for your security manager. Export it with your reviewer attestation. This becomes the executive summary for this investigation cycle.
Run a Vision cloud investigation: Ask Vision to identify the highest-risk patterns in your cloud environment. Review the assumptions and verify at least three cited findings are current.
Create a cluster-based treatment plan: Use the Vision analysis to create one treatment plan addressing the shared root cause of the highest-priority cluster.
Draft and attest a cloud risk narrative: Generate a Vision narrative for your security manager. Add your reviewer attestation before sharing.
Knowledge Check
What is Vision AI's primary role in cloud security investigation?
To automatically remediate cloud misconfigurations by pushing configuration changes through the connected provider APIs.
To surface patterns, prioritize high-risk finding clusters, and generate narrative summaries — all requiring human review before use as governance outputs or remediation decisions.
To replace the Framework Explorer by automatically mapping cloud findings to compliance frameworks without manual configuration.
To monitor cloud environments in real time and alert on new misconfigurations within seconds of their creation.
Move on when you've run a Vision investigation and created a cluster-based treatment plan.
